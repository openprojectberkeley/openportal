# Supabase migrations

The database schema for this project is managed in the Supabase dashboard. These
files capture the schema/RLS changes that have been introduced alongside the app
so they're reviewable and reproducible.

Each file is written to be **idempotent** (`if not exists`, `create or replace`,
`drop policy if exists`), so it's safe to run against the existing database — run
them in order in the Supabase SQL editor.

| `0002_infosesh_attendance_rls.sql` | `is_board_or_exec()` + RLS for infosession codes. |
| `0003_coffee_chats_one_per_person.sql` | Optional unique index: one chat per applicant per member. |
| `0004_app_settings_coffee_chat_window.sql` | `app_settings` table + `is_vp_tech()` + RLS for the coffee-chat window. |

| `0012_portal_types.sql` | Adds `portals.type` (general/project/exec) + `project_id`; `is_pm()`; derives project-portal membership in `is_portal_admin`/`is_portal_member`; reworks portal insert/update/delete RLS (exec any type, PMs general/own-project, exec delete-only) + creator-admin trigger. |
| `0013_project_portal_membership_sync.sql` | Materializes project-portal rosters into `portal_members` (`managed` flag): populate-on-create + sync triggers on `project_members` (member→member, PM→admin), locks managed rows in RLS, drops the derived branches from the membership helpers, and backfills existing project portals. |
| `0014_portal_owner_admin.sql` | Portal creator (exec or PM, any type) gets a locked `is_owner` admin row; owner rows are RLS-locked and never demoted/removed by the project-sync triggers. |
| `0015_portal_icons.sql` | Adds `portals.icon_url`; public `portals` Storage bucket + RLS (public read, write gated by `is_portal_admin(portal_id)` on the `{portal_id}/icon.jpg` path). |
| `0016_project_types_and_applications.sql` | Adds `projects.type` (studio/launch, default launch), `difficulty` (1-5), `estimated_members`, `num_subteams`; CHECK requiring a client for Studio; folds PMs into `is_board_or_exec()` (board = exec + PMs); `applications` + `application_rankings` tables + RLS (applicant manages own, board/exec read all). |
| `0017_project_pm_update.sql` | Widens `projects` UPDATE RLS so a project's PMs (not just exec) can edit that project's details; insert/delete stay exec-only. |
| `0018_project_difficulty_levels.sql` | Changes `projects.difficulty` from a 1-5 smallint to named levels (`beginner`/`intermediate`/`advanced`) with a matching CHECK. |
| `0019_project_type_exec_only.sql` | BEFORE UPDATE trigger on `projects`: only exec can change a project's `type` (Studio/Launch); PMs can still edit other fields. |
| `0020_application_questions_and_drafts.sql` | Adds `applications.status` (draft/submitted, `submitted_at` now nullable); makes `application_rankings` draft-friendly (rank no longer unique, `essay` nullable, adds `completed`/`updated_at`); adds `project_questions` (per-project custom questions, RLS exec/PM) + `application_answers` (applicant responses, RLS own/board+exec-read). |
| `0021_application_rankings_soft_remove.sql` | Adds `application_rankings.ranked` (bool). Removing a project from the ranking soft-removes it (ranked=false) so its essay/answers survive and re-adding restores them; only ranked=true rows form the current ranking. |
| `0022_application_periods_and_acceptance.sql` | Adds `application_periods` (named cycles: name/window/status draft-open-closed, RLS read-all + exec-write) + `applications_open()`/`current_application_period()` helpers. Extends `applications` with `period_id`, `accepted_project_id`, `reviewed_at`/`reviewed_by`; widens status CHECK to draft/submitted/accepted/rejected; switches uniqueness to one-per-applicant-*per-period* (seeds an initial open period + backfills). Adds `accept_application`/`reject_application` SECURITY DEFINER RPCs (board/exec; accept places the applicant on a project via `project_members` and sets `members.active=true`). Gates applicant writes (applications/rankings/answers) on `applications_open()`. Adds `is_returning_member()` (= `members.active`); first-timers (inactive) may only rank OP Launch projects (RLS on `application_rankings` + a guard in `accept_application` blocking Studio placement of a first-timer). |
| `0023_application_status_drives_open.sql` | Redefines `applications_open()` / `current_application_period()` so a period's `status = 'open'` alone opens applications, independent of its start/end window (which becomes an informational schedule). Exec can open a period early or keep it open "outside window" without editing dates. |
| `0024_coffee_chats_release_own_booking.sql` | Adds an additive permissive `coffee_chats` UPDATE policy (`coffee_chats_applicant_release`) letting an applicant null out a booking that is currently theirs (`using applicant_id = auth.uid()`, `with check applicant_id is null`). Fixes Cancel silently failing for chats whose member isn't the actor, where releasing the slot (applicant_id → null) failed the pre-existing WITH CHECK. |
| `0025_coffee_chats_duration.sql` | Adds `coffee_chats.duration_minutes` (default 30) + CHECK restricting it to (15, 20, 30). Backs the switch from hour-long group sessions to duration-tagged sub-slots (15m→4 sub-slots/1 seat each, 20m→3/2, 30m→2/3) within each hour tile. |
| `0026_notifications.sql` | `notifications` table + RLS (owner select/update/delete; self-insert only for `type='reminder'`) + partial unique index for idempotent client reminders + `notify_coffee_chat_counterparty()` SECURITY DEFINER RPC for cross-user booking/cancel/location notices (derives recipient from the seat row, authorizes the caller). Powers the in-app notifications bell. |
| `0027_coffee_chats_host_release.sql` | Additive permissive `coffee_chats` UPDATE policy (`coffee_chats_host_release`) letting a host null out a booking on a slot they own (`using member_id = auth.uid()`, `with check applicant_id is null`) — the host-side mirror of 0024, enabling host cancellation. |
| `0028_coffee_chats_location.sql` | Adds `coffee_chats.location` (per-seat meeting link/place) + `members.default_chat_location` (host default that new availability inherits) + explicit `coffee_chats_host_update_own` policy. |
| `0029_coffee_chat_cancellations.sql` | `coffee_chat_cancellations` audit table (RLS insert/select own) backing the applicant cancel rate limit (5 per rolling 24h), since a released booking leaves no record of who cancelled. Includes an optional commented BEFORE-trigger for hard enforcement. |
| `0030_coffee_chats_allow_repeat_bookings.sql` | Drops the all-time `coffee_chats_one_per_person` unique index from 0003 so a member can book another chat with someone after a past chat. "One upcoming chat per person" is still enforced by the app's future-only pre-check (Postgres can't express a future-only partial unique index). Supersedes the DB constraint added in 0003. |
| `0031_project_portal_sync.sql` | Makes project portals a projection of their project. Adds `projects.icon/icon_url/color` + a public `projects` Storage bucket (write gated by new `can_edit_project()` = exec or the project's PM). Auto-creates the `type='project'` portal on project insert (`create_project_portal` trigger; the 0013/0014 roster+owner triggers still fire), syncs name/description/icon/icon_url/color project→portal on project update (`sync_project_to_portal`), and locks those five fields on the portal (`lock_project_portal_fields` BEFORE-UPDATE reverts portal-side edits to the project's values). Restricts portal INSERT to exec (drops 0012's PM branch). Backfills: seeds project icon/color from existing project portals, creates portals for projects lacking one, and reconciles every project portal to its project. |
| `0032_portal_membership_defensive_project_scope.sql` | Defense-in-depth for project-portal visibility: re-adds the derived project-membership branches to `is_portal_admin`/`is_portal_member` (a union with 0013's explicit-row checks), so a project's members/PMs see exactly and only their own project's portal even if the materialized `portal_members` roster ever drifts. Cannot widen access across projects (the derived branch is scoped to the portal's own project + `auth.uid()`). |
| `0033_project_members_scope.sql` | Restricts the project roster: replaces 0005's world-readable `project_members_select` (`USING(true)`) so the full roster is visible only to exec and to fellow members of the same project (via new SECURITY DEFINER `is_project_member()`), while PM rows (`is_pm=true`) stay world-visible for the applicant coffee-chat and ranking flows. Basic `projects` info stays open. |
| `0034_project_portals_no_owner.sql` | Project portals now have **0 owners** — governed entirely by their project roster (managed PM admins). Redefines `portals_grant_creator_admin` (from 0014) to skip `type='project'` portals, so creating a project no longer makes the creator a locked owner of the auto-created portal (general/exec portals still grant creator ownership). Backfills existing project portals: clears `is_owner` on rows that are also `managed` (revert to plain synced admin) and deletes owner-only rows (creators who were never project members). |
| `0035_coffee_chat_booking_rpc.sql` | Fixes "booked where they shouldn't have been". Adds SECURITY DEFINER `book_coffee_chat(member_id, meeting_time)` that atomically re-checks every booking rule (6-hour minimum notice, in-window, not self, one-upcoming-per-person via a per-pair advisory lock) and claims one open seat (`for update skip locked`) in a single transaction — replacing the racy client-side pre-check + conditional UPDATE. Drops the permissive `"Applicant can claim an open spot"` UPDATE policy so booking can only happen through the RPC. Adds a `coffee_chats_no_self_book` CHECK (cleans existing self-books first). Keep the notice window in sync with `COFFEE_CHAT_MIN_NOTICE_MS` in `src/lib/coffee-chat-window.ts`. |
| `0038_coffee_chat_message_and_rich_notices.sql` | Adds `coffee_chats.message` (optional free-text note a booker attaches when booking, stored permanently on the seat). Recreates `book_coffee_chat` with a 3rd optional `p_message` param (drop+recreate since the arg list changes; default keeps 2-arg callers valid) that trims/caps it to 500 chars and stores it on the claimed row. Enriches `notify_coffee_chat_counterparty` (same signature) to read `location` + `message` from the seat row and both parties' display names from `members`, composing specific title/body copy that always names the counterparty and states the date/time and location (e.g. "New coffee chat with Jane Doe" + location + message) instead of the old generic "someone"/"your host" wording — the in-app bell and the 0037 email both inherit it. |
| `0037_notification_emails.sql` | Email delivery for important notifications via SMTP2GO. Enables `pg_net`; adds `members.email_notifications` (bool, default true — per-member opt-out honored by the sender) and `notifications.email_sent_at` (idempotency stamp). Adds a SECURITY DEFINER `on_notification_email()` AFTER-INSERT trigger on `notifications` that, for the cross-user coffee-chat types only (`chat_booked`, both cancellations, `location_added/updated` — never `reminder`), reads the `send-notification-email` Edge Function URL + shared secret from Vault (`notification_email_url` / `notification_email_secret`) and `pg_net.http_post`s the notification id to it. Skips silently if the Vault secrets are unset, so it never blocks an insert. Requires the Edge Function (`supabase/functions/send-notification-email`) + one-time Vault setup (commented at the bottom of the file). |
| `0036_apply_default_chat_location.sql` | Adds SECURITY DEFINER `set_default_chat_location(location)` so saving the host default no longer just changes what new/open slots resolve against. It sets `members.default_chat_location` **and** rewrites the caller's upcoming booked `coffee_chats` rows (`applicant_id` set, `meeting_time >= now()`) whose `location` is null or still matches the **old** default — propagating the new value while preserving genuine custom per-slot locations. Attendees of changed rows are notified via `notify_coffee_chat_counterparty` (`location_added`/`location_updated`); clearing the default resets non-custom rows to null silently. Open (unbooked) rows stay null (they already resolve against the live default). Returns the count of rewritten chats. |
| `0039_member_timezone_notifications.sql` | Fixes cross-user coffee-chat notifications rendering the meeting time in UTC (the Postgres session default) instead of the recipient's real timezone — the in-app pages/emails already convert correctly client-side via `.toLocaleTimeString()`, but notification title/body text is composed once, server-side, as plain text. Adds `members.timezone` (IANA name) + SECURITY DEFINER `set_member_timezone(timezone)` (validates against `pg_timezone_names`, no-op if unchanged) for the client to keep in sync with the browser's detected zone. Recreates `notify_coffee_chat_counterparty` (same signature) to localize `v_when` via `v_time AT TIME ZONE coalesce(recipient's timezone, 'UTC')` instead of the bare session-default `to_char`. |
| `0040_notify_booker_on_book.sql` | Also notifies the BOOKER (applicant) on `chat_booked`, not just the host — so the booker gets the confirmation email + calendar invite too. Recreates `notify_coffee_chat_counterparty` (same signature as 0039): the `chat_booked` branch now inserts a second `chat_booked` notification addressed to the applicant with booker-facing copy ("You booked a …") localized to the applicant's own `members.timezone`. No email-trigger or edge-function change needed — the extra row is still type `chat_booked`, which the 0037 trigger forwards and `send-notification-email` turns into an ICS `REQUEST` with ATTENDEE = the booker and the same `coffee_chat_id` UID. |
| `0041_notify_canceller_on_cancel.sql` | Also notifies the CANCELLER on both cancellation types, so a cancel clears the event from BOTH calendars (previously only the counterparty got the `METHOD:CANCEL` invite, leaving the canceller's own copy — added by 0040's booking invite — to linger). Supersedes 0040 (same signature; keeps the booker-on-book block): the cancellation branches now insert a second `chat_cancelled_*` row addressed to the actor (`auth.uid()`) with self-facing copy ("You cancelled …") localized to the actor's own timezone. Same-type row → 0037 trigger forwards it → `send-notification-email` emits a `METHOD:CANCEL` for the same `coffee_chat_id` UID with ATTENDEE = the actor. |
| `0042_member_status_enum.sql` | Replaces `members.active` (boolean) with `members.status` (`public.member_status` enum: `active`/`inactive`/`non_member`/`blacklisted`, default `non_member`). Backfills from `active` (`true` → `active`, `false`/null → `non_member` — no historical data to distinguish rolled-off/blacklisted members, an accepted documented gap) then drops the old column. Redefines `is_returning_member()` to `status in ('active','inactive')` (a rolled-off member still counts as returning for OP Studio eligibility) and `accept_application()` to set `status = 'active'` on accept and use the same `in ('active','inactive')` check for its own Studio-eligibility guard, keeping the two in sync. Adds board/exec-gated SECURITY DEFINER `set_member_status(p_user_id, p_status)` backing the new admin status control, plus a `members_status_guard` BEFORE UPDATE trigger blocking any self-write to `status` outside that RPC (defense-in-depth, since the dashboard-managed `members` RLS isn't visible from migration history). No RLS block on blacklisted applicants submitting — deliberately out of scope. |
| `0043_application_profile_and_resume.sql` | Adds optional applicant-background fields to the written application. New `applications` columns: `tech_area_rankings` (jsonb `{ areaKey: 1..5 }` interest ratings), `tech_classes` (jsonb `[classKey]` checklist), `tech_classes_other` (text), `resume_path`/`resume_filename` (the uploaded resume), and `about_note` (free-text "anything else"). No new table RLS — the applicant already owns their `applications` row (0022 self + `applications_open()` policies). Also creates a **private** `application-resumes` Storage bucket (path `{user_id}/{period_id}/resume.<ext>`) with `storage.objects` policies: owner (first path segment = `auth.uid()`) may insert/update/delete; read is owner **or** `is_board_or_exec()` so reviewers can mint signed URLs. |
| `0044_resume_parsed.sql` | Adds `applications.resume_parsed jsonb` — the applicant's uploaded resume parsed (client-side, heuristically) into sections (contact/education/experience/projects/skills/awards/other) and then edited/confirmed by them. No new RLS (applicant owns their row via 0022; board/exec read via the 0016 applications SELECT policy). **Reverted by 0045.** |
| `0045_remove_application_profile_and_resume.sql` | Partly reverts the resume work: removes the private Supabase resume bucket + heuristic parsing (resumes now go to Google Drive — 0046). Drops the four `application_resumes_*` storage policies and the `applications` columns `resume_path` and `resume_parsed`. **Keeps** the rest of the "About you" section (`tech_area_rankings`, `tech_classes`, `tech_classes_other`, `about_note`) and `resume_filename` (reused for the Drive filename). Idempotent. **The private `application-resumes` bucket must be emptied + deleted via the Storage API/dashboard** — Postgres blocks direct deletes from `storage.objects` (`storage.protect_delete()`), so the bucket removal is not in the SQL. |
| `0046_resume_drive_link.sql` | Resumes are uploaded to a shared Google Drive folder by the `upload-resume-drive` edge function (service account) and reviewed in the team's existing Drive-based tool. Adds a light reference on `applications` so the in-app reviewer modal can link to the file: `resume_drive_file_id`, `resume_drive_url` (webViewLink), `resume_filename` (original name), `resume_uploaded_at`. No new RLS (edge function writes with the service role; reviewers read via the 0016 applications SELECT policy). |
| `0047_president_vp_tech_parity.sql` | Grants President the same special capabilities VP Tech has (both are already exec, so this only affects things gated on the literal "VP Tech" role rather than on exec generally). Adds `is_president()` (mirrors `is_vp_tech()` from 0004) and combinator `is_vp_tech_or_president()`. Replaces the `app_settings_insert_vp_tech`/`app_settings_update_vp_tech` policies (coffee-chat booking window) with generically-named `app_settings_insert`/`app_settings_update` using the combinator. The "view as" role-simulation toggle is extended to President too, but that's app-side only (`src/lib/roles.ts`'s `ELEVATED_ROLE_NAMES`) — no DB object backs it. `send-support-email`'s recipient list is deliberately left VP-Tech-only (a support-routing decision, not a permission). |
| `0049_member_resume.sql` | Reverts the Google Drive resume upload (0046) — that route was blocked by the org's service-account-key policy. Resume is now **member-level** (one per person, ever): adds `members.resume_path`, `members.resume_filename`, `members.resume_uploaded_at` (written by the applicant under the existing `members` self-update RLS; read by board/exec via the open `members` SELECT). Drops the `applications` Drive columns (`resume_drive_file_id`, `resume_drive_url`, `resume_filename`, `resume_uploaded_at`). Re-creates the private `application-resumes` bucket's storage policies (0045 dropped them), keyed to the `{user_id}` first path segment — owner may insert/update/delete; read is owner **or** `is_board_or_exec()`. The app stores a single object per user at `{user_id}/resume.<ext>` (500 KB cap), replaced on every upload. |
| `0050_application_profile_fields.sql` | Re-adds the optional "About you" fields to `applications` (added in 0043, dropped in the 0045 rollback, now brought back): `tech_area_rankings` (jsonb `{ areaKey: 1..5 }` interest ratings), `tech_classes` (jsonb `[classKey]` checklist), `tech_classes_other` (text), `about_note` (free-text "anything else"). Applicant-level, per period. No new RLS — the applicant owns their `applications` row (0022 self + `applications_open()`); board/exec read via the 0016 SELECT policy. Resume stays separate (member-level, 0049). |
| `0051_op_studio_returning_member_priority.sql` | Makes returning-member status a **priority** for OP Studio rather than a **requirement**. Recreates the `application_rankings` insert/update policies without the `is_returning_member() or launch` restriction (first-timers may now rank Studio projects too) and drops the first-timer Studio guard from `accept_application()` (board/exec can now place any applicant on a Studio project). `is_returning_member()` is left intact but no longer gates Studio ranking/acceptance; the UI surfaces the priority as a note. |
| `0052_account_exists_rpc.sql` | Adds `public.account_exists(text)`, a `SECURITY DEFINER` function that reports whether a `@berkeley.edu` email already has an account and which provider(s) it uses (`found`, `has_password`, `has_google`). Lets the signup form pre-check for a duplicate **before** calling `signUp` and steer returning users to the right sign-in method (most signed up via Google). Disclosure is minimal by design — booleans only, gated to `@berkeley.edu` so it isn't a general email-enumeration oracle; execute granted to `anon`, `authenticated`. Advisory UX only; the unique email in `auth.users` remains the real duplicate guard. |
| `0053_application_period_stats.sql` | Adds `public.application_period_stats(p_period_id uuid)`, a read-only `SECURITY DEFINER` RPC returning the application funnel for one period as a single row: `empty_drafts`, `unfinished_drafts`, `submitted`, `accepted`, `rejected`. A draft is **empty** when it has no content anywhere (no non-empty `essay` on any ranking and no `application_answers` rows — empties are stored as NULL / never inserted, and content is counted across all rankings incl. soft-removed `ranked=false` ones), **unfinished** once it has an essay or ≥1 answer; the three status counts cover the completed apps. Guarded with `is_board_or_exec()` (mirrors accept/reject_application; board/exec already read these rows via the 0016 SELECT RLS, so it exposes nothing new — the exec-only visibility is enforced client-side). Backs the funnel tiles shown above the list on the Applications manager page. Execute granted to `authenticated`. |
| `0055_coffee_chat_location_is_custom.sql` | Adds `coffee_chats.location_is_custom boolean not null default false` and rewrites `set_default_chat_location` to propagate a default change to **every** upcoming booked seat that is not a manual override (`location_is_custom = false`), regardless of its current value — replacing the old-default value heuristic in `0036` that permanently stranded seats whose frozen location had drifted from the current default. Backfill marks existing seats whose location differs from the host default as custom (preserve-as-manual), so current appearances are unchanged while the inherited-vs-custom distinction becomes stable. `saveSlotLocation` sets the flag true when a host edits one slot and false when cleared; `book_coffee_chat` is unchanged (a freshly booked seat stays non-custom and keeps following the default). |
| `0056_member_pronouns.sql` | Adds `members.pronouns text` and `members.pronouns_public boolean not null default true` (a per-member "visible to everyone" toggle, default ON). Pronouns are collected in onboarding and editable from the profile dialog; when `pronouns_public` is false the public-profile API (`GET /api/members/[userId]`) strips pronouns for other viewers while the owner still sees their own (RLS exposes all `members` columns to any signed-in member, so the gating is enforced server-side, not by RLS). |
